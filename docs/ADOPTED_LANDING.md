# Original project landing

After reviewed adoption, `submit` can execute the existing detached native-task route for Mathy, Main Character, Roboty and Glass Alpha. The source must belong to the enrolled clone and pass its original source-ownership policy. Admission retains the committed range, Git ref and bundle before acknowledging the operation. The source workspace remains owned by its native task manager.

A validated capture interrupted before admission retains the original source-policy selection and candidate metadata. The same request can resume after the native task advances, without claiming that the newer tip was submitted or integrated. Original adapter adoption is reverified; changed authority, clone or policy still blocks. `submit --resume` uses only the original repository/request identity, and the service exposes unfinished capture separately from accepted work. An older intent without recorded eligibility must satisfy the original current-tip check before it can gain this recovery path.

The service rechecks adoption fingerprints, retained source and the selected range. A clean unchanged native task uses the project's `scripts/worktree-land`. A dirty, advanced or unavailable native task uses a separate Git worktree at the exact retained tip under private Contribution state. It contains no uncommitted task work and does not use a Codex-looking path. The original `scripts/worktree-landing-worker --candidate` consumes this explicitly registered snapshot, with the project's selected Node/pnpm environment.

Registration calls the original candidate enqueue export under the compatible landing-flight lock. It compares the reviewed queue scope, retains its prior contents and carries task identity, inherited supersession, Mathy selectors/objective/review epoch and source attribution through that export. Another source's candidate or an active/unresolved flight blocks registration. Original candidate metadata is retained privately before execution because successful original workers remove their queue entries. This retained metadata remains available for receipt validation after restart.

The registration flight releases before the worker acquires its own existing flight/primary lease; there is no second outer primary lease during execution. Push lease credentials and unrelated service-chat attribution are not inherited. The original native task is never staged, reset, stashed, deleted or reassigned. The result explicitly identifies the Contribution-owned snapshot separately, even when an original worker's historical log text calls every retained source Codex-owned.

Mathy's explicit combined message goes through its existing `--message-file` route. Its original canonical receipt validator, selector requirements and successful native reconciliation remain mandatory. The other three projects retain their integration-only message/attribution and `validation_status: not_run` policies; generic message overrides are rejected. No publication follows landing.

Completion requires the original candidate-specific receipt validator, reachable landed Git identity, clean primary and original source-worktree completion guard against the executed source. An exit code alone cannot establish integration. A nonzero exit after promotion may still be reconciled from that complete proof. Missing receipt, unsuccessful native reconciliation or a failed completion guard retains uncertainty and blocks replay. `runs reconcile` observes the original receipt/guard without rerunning a dispatched worker. A stopped request that never registered a candidate or dispatched its original worker can explicitly resume its unchanged selection after its processes stop. Original project repair remains authoritative.

Current boundary: adopted two-Mac owner transitions and cross-host imported-source admission remain blocked until all cooperating legacy writers, including older task checkouts, are fenced and the sender's source-policy attestation is transferred and verified. Local committed capture does not imply that remote trust boundary is complete. Shallow, submodule and LFS histories retain their explicit unsupported/blocker states.

`tests/adopted-landing.test.mjs` exercises the service against synthetic project entry points for all four policy families using disposable Git histories. It covers unchanged native ownership, dirty/advanced task preservation, exact captured commits, original metadata, explicit Mathy messages/selectors, flight contention, separate lease ownership, post-promotion failure, normal queue removal, retained receipts and completion-guard repair without duplicate integration. These tests verify adapter orchestration; they do not replace real-project worker parity, expensive project suites or live cutover qualification.

The separate [original module API check](verification/original-landing-parity.json) imports all four current project state/entry modules and exercises their eligibility, enqueue, receipt rejection and normal queue removal APIs against disposable histories. It does not run their live workers or modify those projects. This caught the original `.nvmrc` enrollment mismatch and confirmed that Mathy removes successful candidates, making retained requirements necessary. The recorded check used Node 24.21.0; it does not qualify the full Mathy/Glass Alpha worker environments pinned to 24.19.0. The repeatable runner is `scripts/check-adopted-landing-parity.mjs ADAPTER_ID=/absolute/project [...]` after building Contribution.
