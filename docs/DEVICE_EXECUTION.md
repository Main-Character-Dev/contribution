# Device execution checkpoint

Remote Devices now has scoped admission and execution inside the existing engine journal and scheduler. It has no separate daemon or automatic phone action. The module defaults off. Host, device, project/app identity, policy, context and operation scope are checked before admission and again before dispatch. Revocation stops later effects without claiming to undo a dispatched effect.

`devices status` separates host readiness, physical trust, developer service, exact-context capabilities and ownership. Cached observations cannot remain callable. An ownership lease expiry never grants a new owner; unconfirmed prior activity blocks mutation. The selected execution host is independent of canonical Git authority.

Each device receipt retains the canonical schema, operation identity, immutable intent, qualification budget, attempt and separate effects. Install and launch are never collapsed into one success. Retained artifacts are checked again before dispatch, and an installed-app reference must still identify the approved phone/app/build. A successful CLI exit alone cannot establish device readback. Unknown effects block the device and require observation; reconciliation never repeats installation or an undispatched launch.

Qualification is a separate route through registered project plans. It can investigate unverified support under its exact context, operation scope, at most three attempts and a finite deadline. It cannot bypass trust, signing, ownership or project foreground guards. Completing a qualification operation does not automatically promote support. Promotion requires reviewed observed evidence, retained successful operations and exact context. Cold-cellular support additionally requires affirmative absence of prior session, usable Wi-Fi and USB, plus observed cellular use.

`tests/devices.test.mjs` uses a deliberately marked fixture backend and two evidence modes. These executable fixtures cover independent install/launch outcomes, lost readback and observation-only reconciliation, revocation and changed artifacts/context while queued, bounded qualification, rejection of fixture authority, expired ownership and warm-versus-cold capability separation. They do not establish any physical-device capability.

The native CoreDevice adapter has bounded inventory and fixed command forms. It keeps raw hardware identifiers in private state and exposes opaque references. It checks app signatures, provisioning, eligible physical identity, team, entitlements, bundle/build identity and sealed materialized app bytes before installation. Deprecated CoreDevice dictionaries are handled explicitly; unknown shapes stop with a protocol reason. Inventory does not prove absence of an external Xcode/test/debug session, establish signing readiness or infer the actual network scenario.

The [qualification fixture app](../apps/ios-qualification/README.md) now builds unsigned for Simulator with persistent records, draft/configuration, simulated pending work and a Keychain continuity check. No physical update or data-continuity claim follows that build. Native provisioning parsing has a focused fixture covering plist dates and certificate data; verification extracts typed identity fields rather than converting an entire mobileprovision record into JSON.

Remaining implementation includes complete installed project-profile registration and build routes, go-ios packaging and operation adapters, native process/log/test/debug observation, device ownership release/transfer, artifact transport, optional travel browser access, lifecycle/privacy controls and native UI. Physical qualification, per-host trust/signing and the actual travel caller are deferred to the owner's final setup session. CoreDevice inventory alone does not make those operations available.
