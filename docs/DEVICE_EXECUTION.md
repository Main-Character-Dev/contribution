# Device execution checkpoint

Remote Devices now has scoped admission and execution inside the existing engine journal and scheduler. It has no separate daemon or automatic phone action. The module defaults off. Host, device, project/app identity, policy, context and operation scope are checked before admission and again before dispatch. Revocation stops later effects without claiming to undo a dispatched effect.

`devices status` separates host readiness, physical trust, developer service, exact-context capabilities and ownership. Cached observations cannot remain callable. An ownership lease expiry never grants a new owner; unconfirmed prior activity blocks mutation. The selected execution host is independent of canonical Git authority.

Each device receipt retains the canonical schema, operation identity, immutable intent, qualification budget, attempt and separate effects. Install and launch are never collapsed into one success. Retained artifacts are checked again before dispatch, and an installed-app reference must still identify the approved phone/app/build. A successful CLI exit alone cannot establish device readback. Unknown effects block the device and require observation; reconciliation never repeats installation or an undispatched launch.

Qualification is a separate route through registered project plans. It can investigate unverified support under its exact context, operation scope, at most three attempts and a finite deadline. It cannot bypass trust, signing, ownership or project foreground guards. Completing a qualification operation does not automatically promote support. Promotion requires reviewed observed evidence, retained successful operations and exact context. Cold-cellular support additionally requires affirmative absence of prior session, usable Wi-Fi and USB, plus observed cellular use.

`tests/devices.test.mjs` uses a deliberately marked fixture backend and two evidence modes. These executable fixtures cover independent install/launch outcomes, lost readback and observation-only reconciliation, revocation and changed artifacts/context while queued, bounded qualification, rejection of fixture authority, expired ownership and warm-versus-cold capability separation. They do not establish any physical-device capability.

The native CoreDevice adapter has bounded inventory and fixed command forms. It keeps raw hardware identifiers in private state and exposes opaque references. It checks app signatures, provisioning, eligible physical identity, team, entitlements, bundle/build identity and sealed materialized app bytes before installation. Deprecated CoreDevice dictionaries are handled explicitly; unknown shapes stop with a protocol reason. Inventory does not prove absence of an external Xcode/test/debug session, establish signing readiness or infer the actual network scenario.

The [qualification fixture app](../apps/ios-qualification/README.md) now builds unsigned for Simulator with persistent records, draft/configuration, simulated pending work and a Keychain continuity check. No physical update or data-continuity claim follows that build. Native provisioning parsing has a focused fixture covering plist dates and certificate data; verification extracts typed identity fields rather than converting an entire mobileprovision record into JSON.

Remaining implementation includes complete installed project-profile registration and build routes, go-ios packaging and operation adapters, native process/log/test/debug observation, device ownership release/transfer, artifact transport, optional travel browser access, lifecycle/privacy controls and native UI. Physical qualification, per-host trust/signing and the actual travel caller are deferred to the owner's final setup session. CoreDevice inventory alone does not make those operations available.

## Offline preparation

`devices configure --repo ID --file PATH --expected-revision REVISION --request-id UUID` registers a private schema-validated project profile; the initial revision is `none`. `devices profile --repo ID` inspects it. The new [profile schema](../packages/contracts/schemas/device-profile.schema.json) adds one contract while preserving the twelve original schemas unchanged. Registration does not grant phone operations or physical support. Existing adopted projects remain blocked until their source-selection and activation adapters are preserved.

The generic Xcode adapter selects one explicit project/workspace, scheme, configuration, developer directory, exact Xcode version/build, app identity, manual provisioning selection, deadline and eligible opaque devices. The owner must separately authorize `prepare`. Previously verified physical identifiers remain private and are used only for provisioning membership; the build performs no inventory, trust, tunnel, install or launch call. Missing local signing or dependencies fail with retained build evidence. There is no automatic provisioning update or device registration.

`devices prepare --repo ID --host HOST --device DEVICE --source-tip OID --build-profile PROFILE --request-id UUID` snapshots the exact clean committed source into a Contribution-owned detached build checkout. Build output stays outside that snapshot. Source, toolchain and signed output are rechecked before retention. Shallow, submodule and LFS inputs are explicitly unsupported by this generic route, pending their project adapter. Original task/primary checkouts and unrelated files are preserved.

The immutable archive and materialized app retain source/tree/configuration/toolchain identity, separate archive and app-tree digests, eligible device references and signed identity/provisioning/entitlement evidence. Verification requires an Apple signature for the approved team and profile coverage for the signed entitlements. Preparation explicitly records `deviceAcceptance: not_established_by_preparation`; it neither claims phone ownership nor changes capability qualification. Installing a retained signed build does not require the installation host to possess the build host's signing key; it must independently verify the artifact and target provisioning before dispatch.

Seven offline build fixtures cover no phone access, distinct scopes, isolated inputs, source/toolchain changes, revocation, local failure, cancellation, sealed-artifact recovery and duplicate requests after later profile changes. Interrupted local builds do not become uncertain phone effects. `devices reconcile` can recover a sealed artifact without rebuilding; incomplete outputs remain for inspection. Real Xcode signing, project-specific parity, transfer, installation and data continuity remain unqualified.

Use `devices artifacts list --repo ID` or `devices artifacts get --repo ID --artifact ID` to inspect retained provenance without exposing private local paths. Inspection grants no installation authority. An interrupted build with a still-live or unconfirmed process identity blocks another preparation until that process is reconciled.

## Retained artifact transfer

`devices artifacts transfer --repo ID --artifact ID --from-host SOURCE --host DESTINATION --request-id UUID` uses the existing fixed paired-host SSH envelope and durable operation journal. Transfer direction is independent of the repository's canonical Git owner, but both hosts must have the explicit repository association. Remote Devices must be enabled and the receiving host must have a matching project/app and eligible device scope. Transfer does not create phone grants, acquire phone ownership, install, launch or alter Git authority.

The immutable manifest binds the archive digest, full provenance, materialized app digest, app name and both host identities. Chunks have bounded canonical encoding, exact offsets and durable acknowledgments. After a lost chunk reply, the same request resumes at the retained offset. A lost completion reply is reconciled against the exact retained receipt; even later scope revocation does not rewrite a historically completed transfer into failure. New work still requires current scope. Use `runs reconcile OPERATION_ID` to resume a waiting/interrupted/uncertain transfer.

The receiver verifies archive bounds, digest, safe paths, file kinds, sizes, CRCs and the materialized app tree. It refuses links, traversal, name collisions, encryption, ZIP64, unrecognized compression and decompression beyond the bound. Production receipt verification additionally checks the native signature/provisioning against an approved previously observed physical identity without contacting the phone. The original build provenance remains separate from the receiver's receipt. Streaming archive hashing avoids loading a whole archive into memory.

Current bounded limits are one GiB for archive and expanded app, 256 MiB per member, 50,000 entries, three unfinished transfers per repository and four GiB of conservative incoming reservation. Incomplete or corrupt transfers remain private for reconciliation; storage pressure blocks admission instead of deleting evidence. Scoped pruning remains part of lifecycle work.

Five two-service fixture cases and three native-archive fixture cases cover both directions, lost acknowledgments, changed policy, corrupt bytes, evidence-mode mismatch, distinct logs, later revocation, contained extraction and executable modes. They never invoke a physical backend. Real SSH, cross-Mac signing/provisioning, large-app performance and install/data continuity remain separate qualification.

Run transfer on the selected source service. The optional `--to-host DESTINATION` shorthand selects that destination from the current source host; it does not replace the approved `--from-host` / `--host` contract. The associated companion can now route named operations to the selected service; the actual phone-only travel caller remains unqualified.

Selected-host device commands now forward from the associated companion service through the existing peer channel. The documented `--host` selects the execution host for device operations; `--from-host` selects the source service for artifact transfer. Configuration and new authorization remain local to their selected service. The caller captures the remote profile revision before durable admission and can queue offline against a previously observed revision. Target policy changes require a fresh request; they cannot silently change an accepted build or operation scope. See [PEER_PROTOCOL.md](PEER_PROTOCOL.md).

Remote install lost-reply, policy/grant denial, queued cancellation and observation-only reconciliation fixtures pass. Cancellation of uncertain admission first finds the retained target request or records a no-execution fence. It never creates an install while trying to cancel one. Independent canonical Git work continues when a device setup request needs attention.
