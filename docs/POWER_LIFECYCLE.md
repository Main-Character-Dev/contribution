# Power during accepted work

Settings → Setup provides an explicit **Keep this Mac awake while work runs** preference. It defaults off and is private to this host. The CLI reads it through `service power-policy --json` and changes it with `--file PATH --expected-revision REV --request-id UUID`. The strict [power-policy schema](../packages/contracts/schemas/power-policy.schema.json) contains only `schemaVersion: 1` and the boolean `keepAwakeWhileWorking`. This implements the host preference already specified in the architecture; it grants no phone action or session maintenance.

When enabled, the installed service requests idle-system-sleep prevention only while local scheduler work or an accepted external gate is active. Queued work, offline handoffs, blocked effects, periodic GitHub observation and cached device availability do not hold the Mac awake. Pause prevents new jobs; an already running job can retain its assertion until it finishes. Draining shutdown stops renewal and closes the exact owned child before releasing the service.

The native utility invocation is fixed: `/usr/bin/caffeinate -i -t 45 -w <service PID>`. The inspected local macOS manual documents idle-sleep prevention, timeout and parent-process exit. Each child is bounded to 45 seconds with a 50-second supervisor deadline. No display-sleep assertion, user-activity assertion, global power setting, privilege escalation or wake request is issued. A failed request is visible and retries after 30 seconds while the preference and active work still permit it. It does not fail an otherwise valid Git job.

Status distinguishes inactive, requesting, requested and unavailable. `requested` records a started native process; it is not proof that the operating system has honored the assertion or that a sleeping/offline Mac can execute work. Deliberate sleep, lid closure, shutdown, login and background permission remain actual host boundaries. The physical sleep/wake and installed-service acceptance cases remain unrun.

Preference writes retain the reviewed revision and request identity transactionally. Duplicate replies cannot restore an older preference after a later change. The native client keeps an independent restricted power-settings continuation, so an unresolved install or cleanup request does not prevent reviewing this host preference. Maintenance permits observation while refusing policy changes.

Focused tests use an injected assertion process; they never launch `caffeinate` or change real host power settings. They cover default-off behavior, exact bounded invocation, idle/revoked/shutdown cleanup, duplicate requests, restart, failed assertions and maintenance. The installed CLI fixture reads the default without enabling it. GUI, OS assertion and real sleep behavior require the deferred host qualification.
