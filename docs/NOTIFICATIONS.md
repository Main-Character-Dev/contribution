# Milestone delivery

The same journal owns milestone identity, revision, preferred-host selection and delivery claims. Local gate results and Git delivery share one notification identity per operation, so later delivery replaces the gate milestone. Inactive gates never become gate-pass alerts. Failures, uncertain outcomes, completed device requests, remote workflow failures and current PR readiness remain distinct. Individual successful checks and routine waiting do not produce banners.

GitHub milestones originate only at the repository's canonical host. Paired hosts exchange scoped pending notices and claims through the existing authenticated peer protocol. The destination must match the source host's current notification preference. A second host, a stale revision or a second delivery attempt cannot claim the same milestone. Source-host preferences can select either approved host; an unreachable source cannot grant an offline duplicate. Exact retained operation/log context is available through the same route when a user opens a notification.

A claim is durable before the macOS channel is called. The native client records successful scheduling and checks pending/delivered notifications after restart. If the reply was lost and delivery cannot be observed, the record stays uncertain and the client does not create another banner. This deliberately favors avoiding duplicate interruption; the operation remains visible even when notification delivery is unconfirmed. A newer workflow attempt or stale PR readiness supersedes old alerts, and the client removes matching obsolete notifications.

macOS permission is requested only by the explicit Settings button. Denied permission does not block jobs, disable checks or hide activity. Notification callbacks open the exact retained context only after a user clicks; no routine event raises a window. Settings exposes success/failure preferences and the destination for milestones produced on that Mac. Preference changes use the shared version-checked settings command.

The supporting private IPC routes are `notifications.pending`, `notifications.claim`, `notifications.acknowledge` and `notifications.context`. Claims include repository, origin host, notice/revision and request identity; acknowledgements additionally include the matching retained token. Raw GitHub signed-download URLs and device hardware identifiers are not notification content.

Current proof includes journal claim/replay/uncertainty, gate-to-delivery grouping, preferred-host rejection, obsolete-alert withdrawal, stale-readiness suppression and a two-journal authenticated peer round trip to the exact origin log. Native notification code and settings build. No system permission was requested and no real banner was sent during this implementation. Actual denied-permission, banner activation, reconnect catch-up UX and both-Mac delivery still require installation qualification. Larger catch-up grouping and notice/OS-preference retention remain hardening work.
